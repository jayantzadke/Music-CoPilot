# Code Style — Human-Written Appearance

All generated code must look like it was written by an experienced human developer, not an AI.

## Comments

Comments must read like a real developer's inner monologue — casual, direct, occasionally incomplete sentences. Like sticky notes left for yourself or a teammate, not documentation.

Good:
```typescript
// jiosaavn urls expire after an hour so no point caching longer
// dont call this directly, go through the service
// hashing the refresh token so a db dump cant be replayed
// position is 1-indexed to match what the frontend shows
// this will rarely happen but better to handle it than crash
// 320 first, fall back if the cdn returns a 403
// keeping a copy of the original queue so shuffle can be undone
```

Bad (these scream AI-generated — never write like this):
```typescript
// This function fetches the song details from the external JioSaavn API
// Cache hit: returning cached response for performance optimization
// Validates the input parameters to ensure data integrity
// Implements the repository pattern for database abstraction
// Handles the error case gracefully with appropriate status codes
```

Rules:
- Write like you are leaving a note for yourself at 2am, not writing a readme
- Lowercase always, no capital letters unless it is a proper noun
- No full stops at end of comments
- No colons after the first word ("Cache:" "Note:" "Important:" — all forbidden)
- No emoji, no symbols, no checkmarks
- If the comment just repeats what the code says, delete it
- Sparse is better — most lines need no comment at all
- When you do comment, make it feel slightly offhand, like the developer typed it quickly

## Code Structure

- Avoid over-engineering visible in the structure — no AbstractFactoryBuilderService naming
- Prefer simple, direct variable names that a human would naturally choose
- No excessive type gymnastics — types should help, not show off
- Avoid commenting out large blocks of code — just delete it, that's what git is for
- No TODO comments in shipped code unless they reference a real ticket

## Function and Variable Names

Write names like you are explaining it to a colleague:

Good: getUserPlaylists, isOwner, fetchSong, handleLoginError
Bad: executeUserPlaylistRetrievalOperation, checkOwnershipStatusBoolean

## File-Level Comments

No file-level banner comments like:
```
// ============================================
// Auth Service — handles all authentication
// ============================================
```

Just start writing the code. The file name and folder location already explain what it is.

## General Feel

Read the code back out loud. If it sounds like a tutorial, a readme, or something generated by an AI assistant, rewrite it. It should read like a developer who knows the codebase well just typed it out without overthinking.

## Dead Giveaways — Never Do These

These patterns instantly reveal AI authorship. They are banned:

- Starting comments with "This", "The", "We", "Here", "Note that", "Important"
- Phrases like "for performance optimization", "to ensure data integrity", "to handle edge cases"
- Summarizing what a function does in a comment right above it
- Explaining patterns: "implements the repository pattern", "uses dependency injection"
- Restating the function name in words: `// get user by id` above `getUserById()`
- Headers inside files like `// ---- Authentication ----` or `// === Helpers ===`
- Over-structured variable names: `isAuthenticationSuccessful` instead of `loginOk`
- Writing "gracefully" anywhere — real devs just say "handles" or nothing at all
